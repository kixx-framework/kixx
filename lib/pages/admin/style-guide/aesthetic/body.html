Design Aesthetic

Kixx ships a blank canvas. What follows is a default, not a brand.

This repository includes the Kixx framework, a reference app, and a starter theme. The public website and admin panel provide a neutral, accessible starting point for your project. You own the theme: replace its visible design while retaining the structural conventions that make it maintainable.

That split — structure you keep, look you change — is the organizing idea for the rest of this guide. The sections below spell it out: what is fixed, what is a default, and the accessibility floor that applies either way.

Structure to preserve

These are structural rules, not aesthetic choices. A downstream site keeps them even after it changes every token and modifier.

  • Semantic HTML first — reach for the right element before reaching for a class. A heading is a heading; a button performs an action, a link navigates.
  • BEM ownership — a block owns its elements and its internal layout, never its own outside margin. An element is only ever styled from inside its own block’s rules.
  • Flow spacing — vertical rhythm between siblings is owned by the parent .flow, not by the component. See Layout for the full contract.
  • Composition — page structure is layout primitives → blocks → elements, in that order of responsibility. A layout class never carries block styling; a block never lays out its siblings.
  • One-way color tokens — component → semantic → reference palette. A component rule reads a semantic --color-* token or a component token built from one, never a raw palette value or a color literal.
  • No inline styles — ever. Resolve styling through an existing component, a shared stylesheet, or a page-local page_stylesheet include.

What is a default

These choices give the starter a usable baseline. Revise shared tokens and owning stylesheets for a new design; use modifiers for variants that need to coexist.

  • Typography — a system sans-serif, a fixed type scale, and zero tracking. Choose fonts, sizes, weights, line heights, and tracking for your content. Define shared choices in design-tokens.css and apply them in the owning stylesheets.
  • The palette — a warm-paper-and-near-black-ink base with one link accent and a status family. Change it in the --palette-* tier; see Colors.
  • A small corner radius — 0.25rem on buttons, fields, cards, and callouts, all sharing --control-radius / --radius-md. Change the token to go square or pill-shaped.
  • Visual structure — hairline borders, flat surfaces, and left-edge markers. Replace these devices with the borders, surfaces, shadows, or other treatments your design needs, while preserving layout and block ownership.
  • Hover inversion — buttons flip fill and text color on hover. You can replace this treatment while keeping focus and other control states distinguishable.
  • A single link accent — a restrained starting palette. A project may add brand or decorative colors through meaningful semantic roles; keep status roles distinct.
  • Light and dark schemes with a toggle — a starter feature. A project may choose one scheme, follow system preference, or replace the switching model. Update tokens, scripts, controls, and documentation together.

A typeface can change the rules

The system sans ships without tracking tokens. A condensed gothic set in capitals may need tracking to stay legible. Adding a small --tracking-* family is a valid response to that typeface choice; tracking is not inherently decoration. Document the roles and values in Typography and apply them in the owning CSS rules.

A redesign can change the palette, typefaces, scale, tracking, scheme model, visual structure, and theme-switching machinery while retaining BEM ownership, parent-owned spacing, composition, one-way color tokens, no inline styles, and the accessibility floor. Update this guide to describe the resulting design.

Accessibility floor

These are not optional, in the default theme or in anything built on top of it.

  • Visible focus — every interactive control shows a --color-focus-outline ring on keyboard focus (:focus-visible), never removed.
  • Comfortable targets — buttons and fields hold at least a 2.5rem minimum dimension (WCAG 2.5.8).
  • Token contrast — verify text, controls, and status indicators against their actual backgrounds in every scheme the project supports. Don’t recolor body text to a status hue tuned only for a foreground mark.
  • Native controls stay native — select, checkboxes, radios, file inputs, and range inputs keep their platform affordance. Only text-like inputs and textarea get a custom box.
  • Zoom-safe type — the --text-* ladder stays fixed rem (WCAG 1.4.4); fluid sizing lives on the separate --display-* register and is always bounded, with a rem floor, ceiling, and preferred term.

Guidelines

Do

  • Treat every color, radius, and spacing value here as a starting point for your own site.
  • Change a default through its token first, a new modifier second.
  • Keep the structural rules — BEM ownership, flow spacing, composition — even after restyling everything else.
  • Preserve focus rings, target sizes, and native control behavior no matter how far you take the visual redesign.

Avoid

  • Treating the shipped look as a brand to protect — it is a placeholder.
  • Reaching for a one-off inline override instead of a token or modifier.
  • Restyling a shared block’s elements from a page-local stylesheet.
  • Removing a focus ring, shrinking a target below the floor, or styling a native control’s internals.
