Typography

The starter’s type roles and scale, ready to adapt to your project.

The starter uses a single system sans-serif stack for body text, headings, and UI copy, with hierarchy set by scale and weight. These are starting choices. Adapt the typefaces and roles to your project while keeping semantic structure, legibility, and text enlargement intact.

The shipped font choices

The starter downloads zero text font files. It uses the operating system’s UI face through --font-sans, referenced by --font-body and --font-display. --font-mono serves code, keyboard notation, and copy-field values. A project may load web fonts and revise these tokens in design-tokens.css. Define font loading in shared CSS, keep usable fallbacks, and update the examples here.

Tracking follows the typeface

The starter has no --tracking-* tokens. Its zero letter spacing suits the shipped system sans; it does not prohibit tracking. A condensed gothic set in capitals may need extra spacing for legibility. Add a small reusable family when the chosen typefaces and roles need it — for example, four values if the design has four distinct uses. Document the purpose of each value rather than copying a scale without a use for it.

Apply tracking in the owning typography or component rules, accounting for the explicit letter-spacing: 0 on headings and buttons in reset.css. Test the actual and fallback fonts, wrapping, and enlarged text. Tracking tokens alone do not change the rendered type.

Roles

The starter provides four role families. Their values and font assignments can change with the project:

  • Structural headings — h1–h4, semibold and progressively larger.
  • Display — .type-display-lg through .type-display-sm, bounded fluid type for public mastheads, band headlines, and ledes.
  • Reading & UI text — from .type-body-lg down to .type-caption.
  • Code — the monospace face on a faint sunken ground, for inline tokens like --text-h1.

Typeface sizing by surface

The starter's admin and public pages share a system sans-serif family, with sizing chosen for different jobs. Admin screens use the fixed rem scale documented below because headings label sections inside dense tools. Public pages may also reach for the --display-* register, where oversized text is part of the composition. A project may revise both.

For admin pages, keep typography on the shared fixed rem roles:

  • Predictable density. A section title is the same size every time, so dense screens and data tables stay stable instead of breathing with the viewport.
  • Zoom & accessibility. Fixed rem scales cleanly with browser zoom; vw-based fluid type partially ignores it, working against WCAG 1.4.4 (Resize Text).
  • Simplicity. If a heading is ever too large on mobile, add one discrete breakpoint step — never continuous scaling.

On public pages, body copy, navigation, form text, and ordinary section headings still use the fixed roles. Reserve fluid sizing for display text — a masthead, a band headline, an oversized motif, a lede. Two rules govern it, and neither one is about which file the CSS lives in:

  • Keep the ladders separate. A viewport-coupled step never joins the --text-* scale. Display sizing uses the --display-* register, or its own bounded value.
  • Keep it bounded. Every fluid size needs a rem floor, a rem ceiling, and a rem term in the preferred value.

Where the rule goes is the ordinary question the resolution order in the Frontend Development Guide already answers: a display treatment that recurs across public pages is reusable and belongs in typography.css; one that belongs to a single page belongs in that page’s page_stylesheet. The home page masthead is the second case — a fixed demo document with proportions no other page wants.

Keep fluid type zoom-safe

A clamp() whose preferred value is bare vw ignores browser zoom, which regresses WCAG 1.4.4. Give the minimum and maximum rem values, and make the preferred value carry a rem term so zoom still scales the text while vw only adds viewport response on top:

/* Zoom-safe: rem floor, rem ceiling, rem term in the middle. */
font-size: clamp(2.75rem, calc(2.125rem + 1.8vw), 3.75rem);

/* Not zoom-safe: a bare vw preferred value. */
font-size: clamp(2rem, 6vw, 3rem);
*

Rule of thumb

Line-height is role-dependent, never one global value. Big headings run tight (1.15), reading copy opens up for breathability, and dense UI text sits tighter to save vertical space.

Guidelines

Do

  • Reach for semantic elements first — h1–h4 and p render correctly with no classes.
  • Establish a consistent hierarchy through type roles; keep it readable without relying on color alone.
  • Let paragraphs breathe: .type-body-lg at 1.65 for anything people actually read.
  • Keep a single h1 per screen as the page title.
  • Reach for a .type-display-* role when public display type recurs; keep a one-page treatment in that page’s stylesheet.
  • Keep admin screens on the fixed .type-* roles, whatever the public pages do.

Don’t

  • Treat system fonts or zero tracking as requirements of the framework.
  • Pick a heading level for its size — choose the level for structure, then restyle with a .type-* class.
  • Scatter reusable font sizes across components; revise or extend the shared --text-* roles and document them here.
  • Add a viewport-coupled step to the --text-* scale, or use fluid type in admin panels and shared components.
  • Give a clamp() a bare vw preferred value — it ignores browser zoom.
