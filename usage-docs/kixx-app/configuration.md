# Configuration

How a Kixx App is configured on Node.js and Cloudflare. Paths are relative to
the app directory (the one holding `node-server.js` and
`cloudflare-config.jsonc`).

## The one question that decides where a value goes

> Does the value change **per deploy**, or only **per environment**?

An **environment** (`development`, `local`, `production`, ...) is a class of
deploy that shares behavior. A **deploy** is one specific running instance —
one Node.js process, one Cloudflare Worker version. Two deploys of the same
environment share configuration but not environment variables.

- Per-environment values are **configuration**: `node-config.jsonc` or
  `cloudflare-config.jsonc`, under the `environments` map.
- Per-deploy values are **environment variables**: dotenv files (Node.js) or
  Cloudflare bindings, split again by secrecy (see below).

There is no third place. A value that seems to need both is a sign it should
be split into a config default and a per-deploy override, not a reason to
duplicate it.

## Configuration files

`node-config.jsonc` and `cloudflare-config.jsonc` are JSONC files: JSON plus
`//` and `/* */` comments and trailing commas. JSON5 extensions such as
unquoted keys or single-quoted strings are not supported. Keeping them as
data rather than JavaScript lets tooling read them without executing code.

```jsonc
{
    "name": "my-app",
    "environments": {
        "development": { /* ... */ },
        "production": { /* ... */ },
    },
}
```

Values must be literals, so durations are written out in seconds with a
comment (`"pageCacheReadTtlSeconds": 3600, // 1 hour`) instead of as
arithmetic.

Top-level settings like `name` are rare. Everything else lives under
`environments`, keyed by environment name: every store, cache, logger, and
rate-limit setting that environment's deploys share — for example
`LOGGER.level`, `HYPERVIEW.useTemplateCache`, and `DOCUMENT_STORE`.

The two files are independent: an environment name in one has no obligation
to exist in, or match the shape of, the same name in the other.

At startup the app loads only the selected environment's section. An
environment name with no section in the config file fails startup.

### Which environment is selected

`ENVIRONMENT` selects the config section to load, so it cannot itself live in
configuration.

- The Node.js server (`node-server.js`) uses `--environment` (`-e`), else
  `NODE_ENV`, defaulting to `development`.
- The Cloudflare Worker reads its `ENVIRONMENT` binding, defaulting to
  `development`. `kixx cloudflare create-worker-version` sets this binding
  from its own `--environment` flag.

## Environment variables

Per-deploy values are environment variables, split by secrecy:

| File | Committed | Holds | Cloudflare use |
| --- | --- | --- | --- |
| `.env.<environment>` | yes | Plain per-deploy keys, such as `TRUST_PROXY`, `PORT`, `DATA_DIRECTORY` | Required build input; every value becomes a plain-text binding |
| `.env.<environment>.secrets` | no | Signing secrets and tokens | Not used; secret values live on the Worker |

The secrecy split follows the git boundary. There is no per-key annotation to
keep in sync, and no way for a value to be classified two ways at once.

`example.env` documents every plain key inline; `example.env.secrets` is the
[secrets manifest](#the-secrets-manifest). Bootstrap a fresh clone with:

```bash
cp example.env.secrets .env.development.secrets
```

Then replace the placeholder values.

### Plain keys

| Key | Meaning |
| --- | --- |
| `TRUST_PROXY` | `true` to trust `X-Forwarded-For` when resolving a client IP. Enable only behind a trusted reverse proxy that sets it; otherwise clients can spoof their IP. |
| `PORT` | Node.js server port; see [below](#nodejs-server-port). |
| `DATA_DIRECTORY` | Node.js only; see [below](#data_directory-and-store-paths). |
| `ENVIRONMENT` | Ignored by the Node.js server, which uses `--environment` or `NODE_ENV`. Set by the CLI on Cloudflare. |
| `BUILD_ID` | Identifies one deploy. Generated by the CLI on Cloudflare; never put it in a dotenv file or declare it as a secret. |

### Node.js: merging environment variables

The Node.js server merges three sources, in this order:

1. `.env.<environment>` (or the file named by `--dotenv`)
2. `.env.<environment>.secrets` (the same path with `.secrets` appended)
3. `process.env`

Each file is optional, so dotenv files, `process.env`, or both work. All of
`process.env` is merged; a collision only happens when a dotenv file also
defines the same key.

**A key defined by more than one source aborts startup**, naming the key and
every source that defined it. There is deliberately no precedence rule: a key
with two definitions means one of them is in the wrong place, and resolving
it silently is how a secret ends up bound as plain text.

`--dotenv <path>` names the plain file directly; the secrets file is always
derived by appending `.secrets`, so one flag selects the pair.

### Node.js server port

`node-server.js` listens on `--port` (`-p`), else `PORT`, else `2026`. The
value must be a whole number from 0 to 65535, or startup fails.

```bash
node node-server.js -e production -p 8080
```

### The secrets manifest

`example.env.secrets` lists the secret names a deployment must provide. It is
committed, and it must exist. Each `NAME=value` line declares a required
secret; the value is a placeholder and is ignored. A comment line reading
exactly `# @optional` marks the next entry optional (only comment lines may
sit between the directive and its entry).

```
# Signs CSRF tokens.
CSRF_TOKEN_SIGNING_SECRET=secure-long-random-string

# @optional
# Deleted after the first admin is created.
ADMIN_BOOTSTRAP_TOKEN=change-me
```

The shipped manifest declares:

| Name | Required | Notes |
| --- | --- | --- |
| `DOCUMENT_STORE_CURSOR_SIGNING_SECRET` | yes | Rotating it invalidates every pagination cursor in flight. |
| `CSRF_TOKEN_SIGNING_SECRET` | yes | Rotating it invalidates every open admin form. |
| `ADMIN_BOOTSTRAP_TOKEN` | optional | Creates the first admin; remove it afterwards. Generate one with `kixx admin gen-secure-token`. |

On Node.js, startup checks the merged environment against the manifest:
every required name must resolve to a non-empty string, or startup fails
before any store is opened, naming every missing secret at once. Optional
names are not checked.

Keep code and manifest in sync in this order:

- **Adding a secret:** add the name to `example.env.secrets`, set its value
  on each deployment, then deploy the code that reads it.
- **Removing a secret:** deploy the code that stopped reading it, remove the
  name from `example.env.secrets`, then delete the value from each
  deployment.

On Cloudflare the manifest is also a build input; see
[Worker secrets](#worker-secrets).

### `DATA_DIRECTORY` and store paths

Store paths in `node-config.jsonc` (`DOCUMENT_STORE.path`,
`KEY_VALUE_STORE.path`, `OBJECT_STORE.path`, `CONTENT_STORE.rootDirectory`,
`JOB_QUEUE.path`) are relative, written with `/` separators. They resolve
against the app directory, so `../data/nodejs_app/document_store.sqlite`
lands in a `data/` directory beside the app.

`DATA_DIRECTORY` is an optional, Node.js-only per-deploy value. When set,
those paths resolve against it instead. The `local` environment uses it so a
local instance keeps its own stores instead of sharing the development data.
Leave it unset for every other deployment.

## Job queue settings

`JOB_QUEUE` is a per-environment block in both config files. Every key is
required; the app checks them at startup.

| Key | Platform | Meaning |
| --- | --- | --- |
| `enabled` | both | `false` records jobs but never runs them. |
| `path` | Node | SQLite file. Shipped: `../data/nodejs_app/job_queue.sqlite` (`development`, `production`), `./job_queue.sqlite` (`local`). |
| `pollIntervalSeconds` | Node | Idle wait between passes, so a new job can wait up to this long to start. Shipped: 1. |
| `concurrency` | both | Maximum jobs running at once. Shipped: 4. |
| `drainTimeoutSeconds` | Node | Longest shutdown waits for running jobs. Shipped: 8. Keep it below 10, the server's overall shutdown timeout. |
| `softDeadlineSeconds` | Cloudflare | Stop claiming new jobs after this long in one alarm invocation, then re-arm. Shipped: 20. |
| `durableObjectBindingName`, `durableObjectClassName` | Cloudflare | Bind and export the `JobQueueStore` Durable Object. Leave the shipped values. |
| `retention.completedMaxAgeDays`, `retention.failedMaxAgeDays` | both | Age-based purge of finished jobs. Shipped: 7 and 30. Active jobs are never purged. |

On Cloudflare, jobs run inside a Durable Object alarm, and a job must finish
within one alarm invocation. The default CPU budget is 30 seconds; for
CPU-heavy jobs raise `WORKER_VERSION.limits.cpu_ms` (maximum 300000).

## File upload settings

`FILES` is a per-environment block in both config files. Both keys are
required; the app checks them at startup.

| Key | Meaning |
| --- | --- |
| `maxUploadBytes` | Largest file upload accepted. Shipped: 52428800 (50 MiB). |
| `bucket` | Object store bucket for file contents; must name a bucket under `OBJECT_STORE.buckets`. Shipped: `files`. |

## Cloudflare specifics

The Worker does not read dotenv files. The `kixx` CLI (from the
`kixx-devkit` package) builds Worker versions from these inputs in the app
directory:

```text
cloudflare-config.jsonc
cloudflare-server.js
.env.<environment>
example.env.secrets
.kixx/cloudflare-state.<environment>.json   (optional)
```

This section summarizes what the app expects. The `kixx cloudflare` command
reference covers every check and option.

### Plain bindings

Every value in `.env.<environment>` becomes a plain-text binding. The CLI
owns two names:

- `ENVIRONMENT` comes from `--environment`; a value in the plain file is
  ignored.
- `BUILD_ID` is generated for each uploaded Worker version. Declaring it in
  the plain file, or as a secret name, is an error.

The CLI's dotenv parser supports `NAME=value`, blank lines, whole-line `#`
comments, and quoted values. It does not expand variables, strip inline
comments, or support multi-line values.

### Worker secrets

Secret values are never read from local files or sent by the CLI. Set and
change them on the Worker in the Cloudflare dashboard or with Wrangler. Each
new Worker version inherits secrets from one exact earlier version: the one
recorded in `.kixx/cloudflare-state.<environment>.json`, or, without a state
file, the Worker's latest version. `example.env.secrets` is shared by every
Cloudflare environment.

The source version's secret names must match the manifest:

- Every required name must be set.
- An optional (`# @optional`) name is inherited when set, and skipped when
  not.
- Any other secret on the Worker fails the build.

Changing a secret in the dashboard or with Wrangler creates a new Worker
version, so the recorded version is no longer the latest and the next build
fails as stale. Delete the state file so the next build adopts the latest
version, or restore it from the checkout that made that version.

The state file holds no secret values. Keep it with the checkout that deploys
the environment.

### Worker and resource configuration

`cloudflare-config.jsonc` also carries CLI-only blocks per environment:

- `WORKER` — the Worker name plus Worker-level settings (observability,
  logpush, subdomain). Applied by `kixx cloudflare create-worker` and
  `update-worker`.
- `WORKER_VERSION` — exactly `compatibility_date`, `compatibility_flags`,
  `limits`, `placement`, and `cache_options`. Any other key is rejected.
- `DURABLE_OBJECT_MIGRATIONS` — optional rename, delete, and transfer
  declarations for Durable Object classes.

Resource blocks become bindings: `DOCUMENT_STORE` (D1), `KEY_VALUE_STORE`
(KV), `CONTENT_STORE` (KV and a Durable Object namespace), `JOB_QUEUE` (a
SQLite-backed Durable Object namespace), and one R2 binding per
`OBJECT_STORE.buckets` entry.

**The CLI never creates D1 databases, KV namespaces, or R2 buckets.** Create
them in the Cloudflare dashboard or with Wrangler (`wrangler d1 create`,
`wrangler kv namespace create`, `wrangler r2 bucket create`) and record their
IDs (`databaseId`, `namespaceId`, `kvNamespaceId`) and bucket names in
`cloudflare-config.jsonc`. Each build checks that every configured resource
exists, and fails naming any that is missing. The Durable Object namespaces
are created by Cloudflare when the first version is deployed.

### Sending email

Cloudflare email sending reads `SEND_EMAIL.from` from the selected
environment. The shipped value is a placeholder; replace it with a verified
sender address on an onboarded sender domain before enabling anything that
sends email. `SEND_EMAIL.bindingName` names the Worker's `send_email`
binding (default `SEND_EMAIL`).

### Worker packaging

`cloudflare-server.js` is the entry module. The CLI uploads every statically
reachable module as a separate ES module with comments removed; there is no
transpiling, tree shaking, or minification. The build rejects bare package
imports (including `node_modules` packages), modules outside the app
directory, extensions other than `.js` and `.mjs`, CommonJS, path-casing
mistakes, and `import()` with a non-literal specifier.

`cloudflare-config.jsonc` is not a module and is never uploaded. Before
packaging, the CLI writes `cloudflare-config.generated.js` holding the
top-level fields and only the selected environment. `cloudflare-server.js`
imports it. Do not edit or commit the generated file; change
`cloudflare-config.jsonc` instead.

## Adding a new setting

1. Decide per-deploy vs. per-environment using the question at the top of
   this document.
2. Per-environment: add the key under each relevant environment section of
   `node-config.jsonc` and, if it applies to Cloudflare too,
   `cloudflare-config.jsonc`. Application code reads the selected section
   from `config.env`.
3. Per-deploy, non-secret: add the key to `example.env` with an explanatory
   comment, and to each `.env.<environment>` file that needs a value. Do not
   set `ENVIRONMENT` or `BUILD_ID` for Cloudflare.
4. Per-deploy, secret: add the name to `example.env.secrets` (mark it
   `# @optional` if a deployment may omit it), then follow the order in
   [the secrets manifest](#the-secrets-manifest).
